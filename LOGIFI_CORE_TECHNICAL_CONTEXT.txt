--------------------------------------------------------------------------------
1. WHAT THIS PROJECT IS (TECHNICALLY)
--------------------------------------------------------------------------------
Logifi-Core is a digital flight logbook application with:

  - A Vue/Nuxt SPA (primary product UI)
  - Supabase (Postgres + Auth + Storage + RLS) as cloud backend
  - IndexedDB as local-first cache + offline sync queue
  - Nitro HTTP API routes for privileged / third-party work (Digifi OCR,
    FC View OAuth, credits/payments, guest-sign helpers, lookups)
  - Capacitor 8 iOS shell wrapping the static Nuxt build
  - Postgres SECURITY DEFINER RPCs for signing, roster, endorsements

It is AC 120-78B–oriented: audit trail, SHA-256 entry integrity hashing,
revisions, exports, and immutable signed rows (amend/void rather than edit).

4. HIGH-LEVEL ARCHITECTURE
--------------------------------------------------------------------------------

  [ Capacitor iOS ]  OR  [ Browser ]
            |                    |
            v                    v
     Static Nuxt SPA (.output/public)
            |
            +-- IndexedDB (offline cache + sync queue)
            |
            +-- Supabase JS client
            |     Auth, PostgREST table access, RPC, Storage
            |
            +-- Nitro API (when hosted; Cap uses NUXT_PUBLIC_API_BASE)
                  /api/digifi/*, /api/fcv/*, /api/credits/*,
                  /api/guest-sign/*, lookups, feedback

Patterns:
  - Local-first: load IndexedDB first, merge remote log_entries when online.
  - Privileged domain ops (signing, endorsements, roster links) go through
    Postgres SECURITY DEFINER RPCs — not free-form client table writes.
  - Digifi / FCV / payments / some guest-sign flows need a Node host running
    Nitro; the Capacitor app points API calls at NUXT_PUBLIC_API_BASE.
  - iOS release path: branding → prepare iOS data → nuxt generate → cap sync ios
    (npm scripts like cap:sync / cap:run:ios at root).

5. AUTHENTICATION & AUTHORIZATION
--------------------------------------------------------------------------------
Provider: Supabase Auth (@supabase/supabase-js)

Client:
  - app/lib/supabase.ts — lazy createClient<Database>, persistSession,
    autoRefreshToken, detectSessionInUrl
  - app/composables/useAuth.ts — email/password signup/signin, Google OAuth,
    password reset; global session refs; offline session snapshot retention
    (cachedSupabaseSession); recovery route /reset-password

Middleware:
  - app/middleware/auth.global.ts — initAuth() every route
  - iOS: marketing / often skipped toward /dashboard (or /auth/callback)

Deep links:
  - plugins/02.capacitor-auth-deeplink.client.ts for Cap auth + FCV return

RLS:
  - Table policies keyed on auth.uid()
  - Many sensitive tables revoke direct client writes; mutations via RPCs
  - Server routes: client Bearer JWT; some ops use SUPABASE_SERVICE_ROLE_KEY
    (FCV token store, Digifi uploads, guest-sign completion)

9. DOMAIN CONCEPTS (AS IMPLEMENTED IN CODE)
--------------------------------------------------------------------------------
CFI
  Instructor certificate fields on user_profiles (cfi_number, cfi_expiration);
  snapshotted onto signatures / endorsements when signing.

Roles
  user_profiles.role — STUDENT / INSTRUCTOR / DUAL (and related usage)

Main vs linked instructor
  instructor_student_relationships.relationship_kind ∈ {main, linked}
  Replaces earlier primary/substitute + expiry model (post-00068).
  set_main_instructor RPC.

Flight signature
  One append-only flight_signatures row per entry.
  Methods include roster_pin and guest_drawn.

Signature pending
  Student requests instructor sign; instructor sees pending inbox via RPCs.

Amendment / supersede
  New log_entries row with amends_entry_id pointing at signed original.
  Used for display/totals replacement instead of mutating signed data.

Void
  is_void amendment that supersedes a signed entry (zeroing/superseding)
  without requiring a dual-sign gate on the void itself.

Endorsement
  AC 61-65H catalog (endorsementCatalog.ts, A.1–A.92).
  Statuses: draft | pending | signed | cancelled | imported.
  Flows: request / issue / PIN sign / cancel / import paper record.

Dossier
  Instructor view of a Main student’s logbook summary + endorsements
  (get_student_logbook_summary_for_instructor,
   list_endorsements_for_student_as_instructor).

Paper / imported endorsement
  is_imported + import_source (e.g. paper_manual); no PIN signing.

Digifi
  AI paper-logbook OCR into builder grid; credit-metered; companion phone
  capture via QR token sessions.

FC View / FCV
  External logbook OAuth import; tokens in fcv_integrations; entries tagged
  with fcv_flight_id.

OOOI
  Out / Off / On / In times stored as JSONB on entries.

AC 120-78B
  Compliance framing for audit, integrity hashing, exports, archival.

Logbook type
  flight vs simulator on entries.

11. API / BACKEND PATTERNS (THREE LANES)
--------------------------------------------------------------------------------
Lane A — Supabase PostgREST
  Direct .from('…') for owned rows where RLS allows (entries select/update
  patterns, relationship reads, etc.).

Lane B — Supabase RPC (preferred for privileged domain)
  Roster, signing, guest sign, endorsements, integrity validation, dossier.
  Examples:
    request_instructor_link, set_main_instructor, get_roster_member_profile
    set_signing_pin, sign_log_entry, list_pending_signatures_for_instructor,
    get_pending_signature_entry, guest_sign_log_entry,
    guest_sign_log_entry_for_session
    request_endorsement, issue_endorsement, sign_endorsement,
    cancel_endorsement, record_imported_endorsement
    get_student_logbook_summary_for_instructor,
    list_endorsements_for_student_as_instructor
    validate_entry_integrity
  Triggers handle audit / hash / revision / profile auto-create.

Lane C — Nitro REST (logifi.web/server/api/)
  /api/digifi/scan
  /api/digifi/capture/*  (session, upload, photos, sessions, token get)
  /api/digifi/spread/[spreadId]
  /api/fcv/*             (auth, callback, status, fetch, import, disconnect,

  /api/credits/*         (balance, transactions, add-mock,

17. HOW TO HELP WHEN THE USER ASKS QUESTIONS AWAY FROM THE REPO
--------------------------------------------------------------------------------
When assisting without the codebase:
  - Prefer answers consistent with the architecture above (SPA + IndexedDB +
    Supabase RPC + Nitro for Digifi/FCV/payments).
  - Treat signed flight data as immutable; prefer amendment/void patterns.
  - Treat roster/signing/endorsements as RPC-first, RLS-restricted domains.
  - Do not invent Edge Functions; server logic is Nitro or Postgres RPCs.
  - iOS is Capacitor wrapping static Nuxt; Android is not a first-party app.
  - Offline is real but incomplete on cold empty cache.
  - If proposing schema changes, continue the 20240101000NNN migration style
    and SECURITY DEFINER RPC patterns used for privileged writes.
  - If proposing UI work, dashboard.vue is the main logbook surface and is
    already very large; prefer composables/components over further bloating
    the page when possible.
